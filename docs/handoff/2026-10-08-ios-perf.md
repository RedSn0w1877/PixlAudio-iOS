# iOS performance batch (2026-10-08, branch `perf-ios-oct8`)

An audit of launch, library, artwork, the player and playback turned up work the app does for nothing. This branch
removes the biggest pieces without changing how anything looks or behaves. There is no Mac and no phone in the loop,
so **none of the speed-ups is measured on a device**: the numbers below are what the code now avoids, not stopwatch
readings. The rules these changes leave behind are in `docs/performance.md › Launch, library and artwork`; the API
ledger is in `docs/api-notes.md › Performance batch`.

The Home screen (`App/Features/Home/*`) and the cloud files were left alone on purpose: the "active jobs" branch
(`s25-active-jobs`) is editing them. `AppEnvironment.swift` got two small hunks in `start()`, and
`SpotifyService.swift` two small ones, so a merge conflict with that branch should be trivial.

## What changed, item by item

1. **Rescan with nothing to do** (`ios-launch-rescan`, `ios-library-1`, `ios-data-noop-rescan`). Every launch (300 ms
   in) and every return to the app read the whole song table three times, rebuilt all artists and albums, rewrote the
   scan state and re-queried the music library, even when no file had changed. The scan now keeps a fingerprint of
   everything except the files (all scan options, the folders and where they live, hidden songs, tag overrides, the
   music library's last change, this build) plus the song table's row count, and compares every file's stamp. When
   everything matches it returns at once: no snapshot read, no build, no write, and the store skips its reload.
   Anything that differs (a new, changed or deleted file, a settings change, a hidden song, a tag edit, a different
   song count, a different build) takes the full path, as before. The automatic rescan also runs at utility priority,
   one `JSONDecoder` serves a whole fetch (it was one per row), and the unchanged store reload no longer builds
   lookups nobody reads. For 5,000 songs that is roughly 15,000 row reads and 10,000 decodes per launch and per
   foreground that no longer happen (estimate).
2. **Mini player and library from the cache** (`ios-launch-restore-late`, `ios-data-launch-queue-wait`). The queue was
   restored only after a full database read although the cached library (the same data on almost every launch) was
   already on screen. Now the cache and the saved queue start decoding on the first line of the launch task, the queue
   is restored from the cache, and the database read only reconciles afterwards. With no cache (first launch) the
   order is as before.
3. **Hidden tabs** (`ios-launch-hidden-tabs`, `ios-library-3`). All three tab roots were built at launch, two of them
   invisible, running lists, sorts, indexes and about 55 glass rows. A tab is now built when it is first opened, or by
   an idle build two seconds after launch (Library, then Search). A built tab keeps its stack and scroll position for
   life, as before. If you tap a tab in the first two seconds it is built inside the tap (a little less smooth that
   once; the first fade-in is the tab bar's spring instead of the 0.21 s fade).
4. **Shell under the full player** (`ios-player-1`). The glass tab bar and the tab's glass rows were composited under
   every frame of the opaque player. Once an expand has fully come to rest the shell is faded to zero without
   animation; it is back in the same update that starts any movement of the card (drag, collapse, the player going
   away), so the collapse squash never shows a bare background. Nothing is removed.
5. **Artwork and colours** (`ios-images-1`, `ios-images-2`, `ios-images-4`).
   - The tracks of an album now share one cached cover: embedded art is keyed by a digest of the picture instead of
     the audio file. The scan records the digest (it already has the picture); for a library scanned earlier the first
     decode of each file learns it. Thumbnails and stored colour themes cached under the old per-file keys are found
     and promoted, not decoded again.
   - At most 3 file/embedded decodes and 2 colour extractions run at once, newest first; a request whose last view has
     gone is cancelled while it waits or before its next step. Theme saves are coalesced (one save per burst).
   - At launch one batched read fills the colour mirror with every stored theme (it holds 8,192 now, was 1,024), the
     restored song is themed before it appears, and the shell's theme update reads the mirror without a hop. The mini
     player should show its album colours in its first frame instead of the accent followed by a 0.45 s fade.
6. **Skips and Spotify matching** (`ios-playback-1`, `ios-playback-2`). In gapless mode (the default) a next song from
   the library's files is prepared on the idle deck as soon as the countdown's debounce has run (1.5 s into the song),
   so Next anywhere in the song takes it over at once instead of cutting the audio and building the next song from
   scratch; streamed songs keep the late 4.5 s lead so nothing downloads early (Low Data Mode and cellular decisions
   are unchanged). The Spotify matcher reads its next page with a sorted, limited query on the indexed id, writes a
   batch of matches with one save (it was one per track), counts with the id column only, and the dashboard refreshes at
   most every 2 s while matching.
7. **CI performance numbers** (`ios-launch-perf-ci-debug`). `TransitionPerformanceTests` ran on the Debug build. A
   `[perf]` tag in a commit message now also builds a `PixlAudioPerf` scheme (Release, UI tests only) and runs them; it
   never turns the job red, and its numbers go to the job summary and a `perf-<sha>` artifact. Screenshots and unit
   tests are unchanged.

## What was skipped, and why

- `ios-library-2` / `ios-data-revision-fanout` (one coarse library revision turns a heart tap into a full recompute):
  the optional last item. It touches the Library lists, the detail index, Search and Home (which I was told to leave),
  and "patched lists equal a fresh sort" needs its own proof; not worth the risk in this batch. Plan: split
  `revision` into songs / favourites / artists / playlists revisions, patch the sorted lists by id for favourites-only
  edits, and route the five launch-cache writes through one debounced, ordered writer (`ios-data-cache-writes`).
- Home findings (`ios-home-search-1`, `-2`, and the rest of Home) by instruction.
- Within the items: the Library pager's "only the selected page and its neighbours until first shown" and gating the
  empty states on `model.isComputing` (`ios-library-3`) are not done: with the tab itself deferred the pager work moves
  off launch anyway. The persisted "last album pair" seed for `ThemeStore` (`ios-launch-restore-late`) is replaced by
  the stored-theme read before the restore, which has the same effect without a second source of truth.
- A real-path launch metric (`ios-launch-measure`) is not added.

## Your iPhone checklist

None of this has been on a phone. In plain words:

- [ ] Force-quit PixlAudio, reopen it: the library shows and the mini player is there almost at once, already in the
  album's colours (no accent flash that fades to the album colours).
- [ ] Switch to the background and back a few times while music plays: no hitch, the phone does not warm up. (Before,
  every return rebuilt the library.)
- [ ] Put a new song file into the PixlAudio folder in Files, return to the app: it appears within a couple of seconds.
  Delete one: it goes. Hide/delete a song: it stays gone.
- [ ] Switch tabs: smooth. Do it once within two seconds of opening the app, and once after a few seconds: both fine.
- [ ] Open the full player, swipe the cover carousel, scrub, press the glass buttons: smooth. Drag the player down and
  let go half way: the screen behind it is there the whole time (no black or empty flash at the top).
- [ ] Collapse the player, open it again several times quickly: always the same.
- [ ] Scroll the Songs list and the Albums grid fast, then stop: the covers where you stopped arrive quickly; albums with
  many tracks show the same cover on every track. Album colours on cards do not flash the purple tint on a fresh launch.
- [ ] Play an album from the Songs list in gapless mode (crossfade off) and tap Next several times, also near the start
  of a song: no gap before the next song starts. Let a song end by itself: still no gap.
- [ ] Turn crossfade on, skip, let songs end: unchanged.
- [ ] Play a Spotify or YouTube song as the next one: it still starts after the same short wait (it is not prepared
  early), and on cellular or in Low Data Mode nothing downloads before you reach the last seconds.
- [ ] Spotify: after an import, leave the dashboard open: the counters tick up every couple of seconds, not constantly,
  and the phone stays cool.
- [ ] Instruments › Hitches (optional) over the full player's carousel swipe, and over a cold launch: compare with main.

## What the code now avoids (estimates, not measurements)

| Change | Per launch / foreground | Per interaction |
|---|---|---|
| No-op rescan | 3 full song-table reads, ~10,000 JSON decodes, an artist/album rebuild and a state rewrite at 5,000 songs | none |
| Queue from the cache | the mini player no longer waits for a full database read (0.3 to 1 s) | none |
| Hidden tabs | ~55 glass rows, a search-index rebuild and the Library model's first computation leave the launch frames | none |
| Shell under the player | none | 15 to 25 Liquid Glass surfaces no longer composited under each player frame |
| Cover per picture | an album of N tracks decodes, writes and extracts colours once, not N times | |
| Bounded, cancelled decodes | | a fling no longer starts one decode and one extraction per passing cell, all at once |
| Colour mirror | one batched read instead of a fetch and an animated re-theme per card | |
| Early prepared song | | a skip anywhere in a song starts the next one at once (80 to 250 ms for a local file) |
| Spotify matcher | | ~100 batches x 3 full table scans and ~5,000 commits for a big account become a few reads and ~100 saves |
