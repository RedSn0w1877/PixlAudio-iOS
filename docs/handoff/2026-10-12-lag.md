# Lag report, false crash counting and self-measuring telemetry (2026-10-12, branch `fix-lag-ios`)

Owner: "even though the crashing is done, it is 10x laggier than usual" (build `2b32524`). Evidence: the in-app
Diagnostics export of 2026-10-12 (status, event log, MetricKit JSON). No Mac and no phone here: CI compiles and tests.

## What the export proves

1. **The hang and GPU numbers are from the crash-loop day, not from the current build.** The MetricKit payload (10-09..10-10)
   has about 90 main-thread hangs (250 ms to 2.7 s), GPU time 1095 s against 398 s in front, CPU 133 s. The event log for
   that same day shows the downloaded AI model (a ~900 MB MPSGraph model on the GPU) started on every launch, memory
   warnings at 770-920 MB, and the app killed four times in a row (build `629ff5b`). From `d86db51` on, automatic features
   never load the model (`modelgate denied automatic` in every later launch). There is no hang payload for `2b32524`.
   So the 2.7x GPU/foreground ratio is **very likely the model** (suspected: a payload without call stacks cannot prove
   it), and it is gone in the current build.
2. **Safe mode was stuck ON for the wrong reason: a provable bug.** The log shows
   `previous run ended abnormally; in flight: (empty)` at 10-12 17:14Z with `abnormal in a row: 5`. The run before it
   (launched 13:56:08Z) logged only its launch line: a background or prewarm launch that iOS later ended while it was
   suspended. The old rule was "no clean-exit marker at launch = abnormal", so any such session counted, and two
   abnormal ends made safe mode sticky for ever. While it is ON the launch and foreground library rescan was held back
   (`automatic library rescan held back` 20+ times in the log: new songs would not show up, which feels broken rather
   than slow), plus the banner and interrupted rows. Safe mode itself does not slow scrolling.
3. Thermal state `serious` was logged twice (10-10 15:42Z, 10-11 13:59Z right after the app went to the background).
   Nothing in the current log shows the app running something heavy then (no job lines, `Heavy jobs running: 0`), so it
   is not proven to come from PixlAudio.

## What changed

### A. Abnormal-end detection (`PixlModel/SafeMode.swift`, `AppHealth`)
- `SafeModePolicy.classify(PreviousRunFacts)`: abnormal **only if** the previous run reached its first `.active` scene
  phase (flag `diagnostics.reachedActive.v1`, set at the first `.active`, cleared when the clean marker is written), has no
  clean marker, **and** the in-flight journal still listed heavy work. Everything else is `.ignored`: background launches,
  prewarm, BG-task wakes, force-quits (the app is backgrounded first), jetsam of a suspended app, a foreground end with
  nothing heavy running. A marker written by a run that never was in front (`clean-bg`) is ignored too: it proves nothing.
- MetricKit can still confirm a crash, hang, CPU or disk exception (`metricKitConfirmed`); only payloads newer than the last
  one counted count (the system redelivers old ones).
- One clean **foreground** session resets the count and ends safe mode. A MetricKit-confirmed safe mode needs two. The
  manual switch (`manual`) stays until turned off. Old stored state (5 in a row, sticky) decodes and ends after one clean
  foreground session.
- Settings > Developer > Diagnostics: a **Turn off safe mode** button appears while it is on; the switch stays.
- The automatic library rescan (about 0.1 s incremental) is no longer held back by safe mode
  (`HeavyWorkGate.allowsLibraryRescan`); Emergency stop and a very hot phone still hold it back. The heavy things
  (automatic studio, Spotify matcher, Cloud preparing, model install) stay held back in safe mode.
- Tests: `SafeModeTests` (classification table, expiry, MetricKit confirmation, old JSON), `CrashProtectionTests`
  (background-only run, manual switch, retry then clean session).

### B. Self-measuring telemetry (`App/Services/Diagnostics/LagMonitor.swift`, `LongRunning.swift`, PixlModel `LagPolicy`)
How to read it is below. Overhead: the watchdog is 10 timer wakeups a second on a utility queue (40 ms leeway) and one
`DispatchQueue.main.async` hop per ping, only while the app is active; the hitch meter is one `CADisplayLink` capped at
60 Hz with one small callback per frame, no allocation, only while the app is active; the registry is a counter bump at
the start and stop of an animation. No file I/O on the main thread (events go through `DiagnosticsLog`'s queue). The
meter's callback wakes the main run loop 60 times a second while the app is in front, even when idle: that is the price of
per-frame data. If a later log shows it matters, turn it off first (`HitchMeter.setActive`).

### C. Regression hunt (everything since `7377e83` was reviewed by reading; nothing could be run)
Fixed (provable):
- `JobTelemetry` (the in-flight journal) wrote its file **synchronously on the main actor** at every job start and end, and
  the library scan is a job that runs at every launch and foreground: two atomic file writes (temp file, rename) on the
  main thread each time. They now go, in order, to a utility queue; a read waits for the queued writes.
- The false abnormal and sticky safe mode, and the stale library it caused.

Checked, no main-thread problem found by reading (unchanged):
- ActiveJobs coalescer: event driven (`withObservationTracking`, 250 ms floor), no timer while idle. `StallMonitor`: one 15 s
  task only while a transfer is armed. Memory and thermal: notification and `DispatchSource` driven, not polled.
- `LocalModelGate`, `os_proc_available_memory` and `ProcessInfo` are not called from any view body.
- `ShellCoveredByPlayer`: opacity is exactly 0 or 1 (never a fractional group opacity, so no offscreen pass), flips only in
  `PlayerSheetController` (not per frame), `animation(nil)`.
- Artwork pipeline (3 decodes, newest first, cancelled when nobody waits): designed for scrolling; not shown to starve rows.
- Library list patching (`applyEdit`, favourites path) and the Home recompute (1.5 s wait only for history-only changes,
  utility priority, cancellable).
- Always-running animations: none run while idle; the registry now lists them.

Suspected, not proven (look at the new hang and hitch lines first):
1. `RootView.prebuildHiddenTabs` builds the Home, Library and Search stacks on the main actor 2 s, 2.35 s and 2.7 s after
   launch. If the owner scrolls then, that is a 100-500 ms hitch per tab. Expect `hang ... screen home>...` lines within
   about 4 s of a launch.
2. Opening and closing the full player: the shell comes back from "not drawn" in one frame (15-25 glass surfaces re-rendered
   at once). Expect `hitch` lines for `...>fullPlayer` or for the screen the player closes onto.
3. The lyrics seek bar has a `TimelineView(.periodic 0.25)` that ticks even when paused (listed as `lyrics.seekBar`).
4. GPU time of the glass lists: nothing proves it; MetricKit has no per-screen split.
5. `EmbeddedArtworkIdentity.digest(for:)` takes a lock that the first-use plist read holds (once at launch); `cacheKey` is
   evaluated per row.

## How to read the new lines (Settings > Developer > Diagnostics > Share logs)

Status block (top of the report):
- `Main-thread hangs this run: N, worst X ms`, then `Hang 1..5`, newest first: `time · ms · screen · jobs · thermal · memory`.
- `Frame hitches this run`: the sum of every logged hitch minute. `Long-running`: what was animating or polling, with rates.

Event log lines:
- `hang 412 ms; screen library>albumDetail; scene active; jobs libraryScan; thermal fair; memory 190 MB`: the main thread
  did not answer a ping for 412 ms. Screen = tab, the route on top, `sheet:` or `cover:`, `fullPlayer`. The context is
  captured during the stall.
- `still blocked after 2000 ms; ...`: logged while it is happening (a watchdog kill would otherwise leave nothing).
- `hitch  screen home: 7 of 3512 frames over 1.5x, worst 83 ms`: per screen per minute, only when something hitched. A frame
  is a hitch when it took more than 1.5x its due time (25 ms at 60 Hz). Hangs mean the main thread was busy; hitches
  without hangs usually mean slow layout or rendering.
- Hangs with `jobs` other than `none` point at background work contending with the UI; with `none`, at the screen itself.
