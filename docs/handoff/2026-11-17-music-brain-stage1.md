# Music brain, stage 1 (iOS): running handoff

Branch `music-brain` (cut from `new-ui`). The contract is `docs/brain-spec.md` (v1.1, a copy of the spec). The
reference implementation is the Android repo's branch `music-brain` and its own handoff,
`handoff/2026-11-17-music-brain-stage1.md`. This file is what is actually in this repo: what was built, where it
differs from the spec and from Android, what was cut, what nobody has run. Each milestone appends a section. The
next agent starts here.

**Nothing below has been run on a phone.** Only `Packages/PixlCore` compiles on the Windows machine; `App/` is
compiled by GitHub CI alone. "Works" in this file means: unit tests pass and the code paths were read end to end.

CI for milestone 1a: run `44254580118` (workflow `ci`, commit `167b4b7`) finished green. `core` (Linux): the eight
PixlCore test bundles passed, 2,047 tests. `app` (Xcode 27, iOS 27 simulator): the app built and 649 unit tests
passed, `AutoplayQueueTests` among them. The separate, non-blocking live YouTube smoke step reported one issue, as

## Milestone 1a: "a track from outside the library plays, and the queue does not end"

Spec section 14, stage 1, items 1 to 5. A port of Android's commits `c717409` to `55675b6`.

### What the listener gets (once CI is green and it is checked on a phone)

- When two or fewer tracks are left in the queue, five more are appended: radio neighbours of the last tracks the
  listener chose. Rows the library already has play from the library; the rest play from YouTube audio with no
  library row.
- The queue shows an Autoplay line with a switch above the engine's picks (or at the end of the queue while there
  are none).
- Offline, or with the YouTube source off, picks come from the library and the line says "From your library".
- A track the engine played shows in Recently Played (Home and the full screen). Like or "Add to playlist" makes it
  a library track.
- Kill and reopen: engine items come back as engine items (the Autoplay line is drawn again).

### Item 1: a `yt:` song that was never imported, end to end (spec 7.2, [S1])

An engine track is `Song(id: "yt:<videoId>", contentUriString: "pixlstream://<videoId>")`, built by
`BrainService.queueSong(for:)` from the radio row. It has no SwiftData row. Traced in code, not run:

| Reader | Code | Result for a track with no library row |
|---|---|---|
| Playing it | `DeckItemFactory` resolver chain: `SpotifyPlayableURLResolver.playableURL` has no Spotify id and passes on; `StreamingPlayableURLResolver` and the `pixlstream://` loader read the video id from the URL (`YouTubeSongIdentity.videoId`) | plays from YouTube audio, like a YouTube Music search result |
| Queue, mini player, player | `PlaybackStore.queue` / `current` are `Song` values from the engine | title, artist, album, artwork and length come from the song itself |
| Lock screen, Control Center | `NowPlayingController` reads `engine.queue.current?.song` | fine |
| Artwork and album colours | `albumArtUriString` is the radio row's https thumbnail, as for Spotify songs | fine |
| Lyrics | `LyricsController.ensureLoaded(for: Song)` works on the song's title, artist and length | online lookup works; **a fetched lyric is cached under the `yt:` id** (a cache row, not a library row) |
| Favourite heart, lock-screen Like | `library.song(id:)?.isFavorite ?? song.isFavorite` shows it off; the tap goes through `LibraryEditor.setFavorite`, which now imports the track first | Like = save |
| Song sheet (the ⋮ of a queue row) | `SongOptionsSheet` looked the id up in the library and showed "Song not found" | now falls back to `BrainService.song(id:)`; Play, Like, Add to queue, Next, Playlist work. "Delete" on it removes nothing (and no longer marks the id hidden) |
| Prefetch | `YouTubePrefetcher` uses `YouTubeSongIdentity.videoId(for:)` | prefetches like any streamed song |
| Blocked artists | `BlockedArtistMatcher` matches by artist id, then by folded name; the queue song carries the row's split artist list | a blocked artist's tracks are filtered when the pool is built, and skipped by the engine by name |
| Queue snapshot | `QueueSnapshotStore.songs(for:lookup:)` already rebuilt non-library songs from the snapshot's own fields | restores and plays; now also keeps the tag. The rebuilt song has no split artist list (the snapshot stores one display string) |
| Recently Played | `HomeLogic.mapRecentlyPlayed` joined on the library | now also resolves through `BrainService.engineSongs()` (the `playable` file) |
| History, taste, engagement | `stats.onRecord` writes `playback_history.json`, `MusicTasteStore.record` and an `EngagementRecord` by song id, no join | all three are written for an engine track. **Skipping the two legacy counters for engine tracks is item 6 (milestone 1b)**, as on Android |

| Spotify Connect | Autoplay is off while a Connect device plays | an engine item already in the queue has no Spotify URI; the Connect resolver's search was not traced (spec [S2]) |

`fold`, `cleanTitle`, `Ids`, `BrainHash` give Android's results for every vector in Android's own tests

### Deviations from the spec and from Android, and why

1. **The tables are generated by `tools/brain/gen_tables.py`, from copies of Android's `.tsv` files.** As on Android
   there is no `generateGolden` task yet. `BrainTablesInSyncTests` fails when the Swift tables and the `.tsv`
   copies disagree. Nothing checks that the copies still equal Android's files: copy them again when Android edits
   them.
2. **`BrainKey`**: every dictionary and set of the brain that is keyed by text compares UTF-8 bytes. Swift's
   `String ==` is canonical equivalence (precomposed Hangul equals its jamo); Kotlin's is not. Spec 10.3 rule 13.
3. **`isBlank` / `trim` use a fixed list of spaces** instead of the platform's Unicode tables (Kotlin's
   `isWhitespace` set as of today), so the result cannot change with a Unicode update on one side.
4. **Android's `cleanTitle` behaviour is ported as it is**: a segment that matches several flag rules sets every
   one of them (Android deviation 5).
5. **The stores are in PixlCore, not in `App/Services/Brain/BrainStore.swift`.** `KeyedLogStore`, `BrainTables` and
   `BrainRepository` live in `PixlLibrary/BrainStore/` so they compile and are tested on Windows. The spec's
   `BrainStore.swift`, `CandidatePoolService.swift` and `HostBudget.swift` do not exist as app files: their work is
   `BrainTables`, `AutoplayPool` and `HostBudget` (PixlModel). `BrainEventLog.swift` is milestone 1b.
6. **Record file layout.** `track_alias.pbl` (`key -> [rid, durationMs]`, Android's extra column), `track_merge.pbl`,
   `radio_list.pbl` (facts) and `radio_rows.pbl` (rows; apart from the facts, so a "last used" touch rewrites a
   hundred bytes), `playable.pbl`. `artist_alias.pbl`, `affinity`, `play_event`, `brain_state` are not created:
   nothing writes them before 1b, and a record file needs no schema ahead of time. Rows are JSON
   (`JSONEncoder`, sorted keys), not gzip.
7. **`playable` is keyed by the song id (`yt:<videoId>`)** and has no synthetic id: on iOS the engine track is the
   importer's `yt:` song, so there is nothing to map. It holds the split artist list, not a display string.
8. **Only what is queued is registered in `playable`** (Android registers the whole pool, because its stream proxy
   must find the row to play the track). On iOS the row is needed only to show and save the track later.
9. **The append also waits while the next song is prepared** (`DualDeckEngine.isHandOverPrepared`: a fade running,
   a gapless hand-over scheduled, or the incoming item already built). A queue edit re-plans what plays next and
   would throw that prepared item away. The held batch goes in at the next track change (or after the fade, polled
   every 2 s, 8 times at most). Android defers only during a running transition.
10. **Queue edits never run inside an engine callback.** The engine calls its hooks in the middle of its own state
    changes, so `AutoplayController` evaluates on the next main-actor turn, and the backstop too.
11. **The backstop's "the listener did not press pause"** is: no play or pause event arrived after the queue ended
    (the iOS engine itself sets `playWhenReady = false` at the end). An "end of track" sleep timer that ended the
    queue is never undone (Android deviation 19).
12. **A restored queue adds nothing until playback first starts** (`isRestoringQueue` stays set until the first
    play event). Otherwise a saved queue near its end would send a radio request at app start.
13. **The hooks are direct calls in `PlaybackServices`**, next to `onUpcomingChanged` / `onPlayStateChanged`, not a
    wrapper around those closures (the spec says "chain, do not replace"; the prefetcher's closures are untouched).
14. **The Autoplay line is its own view between rows**, not drawn inside the first engine row (Android deviation
    12). The queue's rows are addressed by display index, which the line does not change. The reorder preview
    assumes equal row pitch, so a drag across the line is off by the line's height while it is in the air.
15. **"Add to queue" inserts above the first engine entry** (Android deviation 13). After a shuffle engine entries
    are mixed in with the listener's; the line is drawn at the first one still to come.
16. **The 4-hour rule reads the newest 400 entries of `playback_history`** (the existing history, with its 5 s
    floor), on the main actor at pick time. `ignoredRids` (6.1 "ignored three times") is wired through the pool
    request and always empty until `play_event` exists (1b).
17. **Anchors, the bridge, FAV / DEEP / ARTIST**: as Android 1a (its deviations 7, 8, 9). No bridge track.
18. **The junk detector is in PixlModel with the fold passed in** (`RadioRules.isJunkRadio(..., fold:)`), because
    PixlNet cannot import PixlLibrary.
19. **An engine queue song has the row's split artist list**; the saved library row is what the YouTube Music
    importer writes (one artist entry holding the display string), so the two differ in `artists` but share the id.
20. **`BrainService.shared`** (a weak static) is how `LibraryEditor`, which is built in three places, reaches the
    engine tracks.
21. **Text**: "Autoplay", "Taizo picks more after this", "From your library", "Finding more like this",
    "Off. The queue ends after the last song" (Android's five strings; English only, as keys).

### Not verified (all of it on a phone; the specific risks)

1. Screenshots: no `[shots]` run was made, so nobody has looked at the queue sheet with the Autoplay line.
2. An engine track actually playing end to end: resolve, audio, seek, crossfade into and out of it.
3. Autoplay appending during real playback; the settle wait; the held append around a crossfade and around a
   gapless hand-over; whether the first appended track is handed over to without a gap.
4. The backstop: `continueAfterQueueEnd` after the engine reloaded the last song paused.
5. The queue sheet: the line's look, the switch, reorder and swipe-to-remove around it, the line at the end under
   the toolbar.
6. Restart with engine items in the saved queue (unit-tested at the data level only).
7. Like / "Add to playlist" on an engine track from the player, the song sheet and Recently Played; that the heart
   turns on; that the saved row survives a library reload.
8. YouTube Music radio from a phone, on cellular, outside the US. Parse time and memory for a 550 KB response
   (`JSONParser` builds a full tree; off the main actor).
9. `fold` and `cleanTitle` over a real library; decomposed Hangul (passes through unchanged on both platforms).
10. App start: no brain code runs before something plays, except Home's first refresh, which reads
    `playable.pbl` if it exists (a small file, off the main actor). Not measured.
11. Spotify Connect with an engine item already in the queue.
12. Record files: only tested on Windows and (in CI) Linux; never on an iPhone's file system.

### How to test

```
cmd //c "ci\\swiftw.cmd test --package-path Packages\\PixlCore --filter Brain --filter Autoplay --filter InnerTubeRadio --filter KeyedLogStore --filter QueueSnapshotBrain"
cmd //c "ci\\swiftw.cmd test --package-path Packages\\PixlCore"

```

On Windows the build sometimes cannot replace a test bundle's `Fixtures` folder ("remove failed ... You don't have
permission"). Delete `Packages/PixlCore/.build/out/Products/Debug-windows-x86_64/*.bundle` and run again. It is not
caused by this work.

On a phone, in this order: tap one song and let it end (related music should follow, the queue should show the
Autoplay line); tap one song and skip to its end at once (the backstop); turn the switch off; airplane mode ("From
your library"); kill the app mid-autoplay and reopen; Like an engine track and find it in the library.
