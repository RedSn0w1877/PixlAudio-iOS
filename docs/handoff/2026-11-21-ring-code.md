# Pixl ring code, iOS (2026-11-21)

Branch `everything`. R1 was the pure core, the renderer and the scanner, ported from Android's `:songtap` ring code
(`handoff/2026-11-21-ring-code.md` on the Android repo). **R2 (this note's second half, "R2: the screen") adds the SwiftUI drawing, the
AVFoundation camera, the flow and the Developer mode diagnostics.** Everything is verified by the Windows PixlCore test run (the same
tests as Android's, with Android's seeds) and the `ci` workflow; **nothing has run on a phone**, and nothing under `App/` can be
compiled here.

The design is `builds/song-tap-code-design/RING-CODE-SPEC.md` (approved 2026-11-20). Order of ways to beam: the Bluetooth tap, the
ring code, the plain QR last ("Use QR code instead" after about 6 s of failed ring scanning, or when the camera cannot run the
scanner). The code carries only a video id and a tag; a song with no video id (never matched) cannot use it and goes the QR way.

## Across the platforms (`Fixtures/songtap-ring`)

`scenes.jsonl` is 12 scenes (a code and integer parameters), `kotlin/*.pgm` are those scenes drawn by Android's **committed**
`RingCodeRenderer` (commit 4f0aaed): I compiled the committed ring sources with `kotlinc` and ran a small harness, no Gradle.
- Swift reads what Kotlin renders: 12 / 12 (`swiftReadsWhatKotlinRendered`).
- The Swift renderer draws the same pictures: byte for byte on Windows (`cmp` on all 12 when the files were made, mean difference 0,
  worst 0). The test allows a mean difference under 0.5 and under 0.2 percent of pixels more than 8 levels off, so another maths
  library may move an edge pixel.
- The reverse (Kotlin reads what Swift renders) follows from the identical bytes, and I also ran Android's committed scanner over
  the Kotlin pictures: 12 / 12, and over its own fresh renders: 12 / 12.
- Android has no test over these files yet. To add one: read `scenes.jsonl` (the keys are in `Fixtures/songtap-ring/README.md`),
  render with `RenderParams`, scan, and compare with `kotlin/*.pgm` or scan the PGMs directly.

## Deviations from the Android port

1. The names: `Gf256.alphaPow` (not `pow`), `RingCodeTimeline.beamTotal(reducedMotion:)` (Kotlin's `beamTotalMs(...)`, a name taken by a constant).
2. ARGB colours are `UInt32` (Kotlin's `Int`); `RingCodeLayout.markerArgb` stays an `Int32` because the golden file prints it signed.
3. The scanner's trace strings are shorter (no number formatting); the sort for the blob list, the outline list and the byte order
   breaks ties by index, which is what Kotlin's stable sort does.
4. Kotlin's Byte arithmetic in the renderer's smudge overlay of the orangeness map is reproduced on purpose (a signed Byte times a
   Double), so the maps match; it only matters as a tie-breaker in the scanner.
5. The long fuzz loops run fewer rounds (Swift Testing runs in debug): see `docs/test-parity.md`.

## Unverified (R1 and R2)

Everything on a device: scan reliability on real cameras, dim light, real screen glare, distance, moire, scan time on an iPhone
(release build, Accelerate for the downscale is not used yet), how the accent-coloured dots look on the plate. The tests render
synthetic pictures with simple glare and smudge models. The blur cliff Android found is the main known weakness: the outline ring
is 25 permille thick, so a frame more than about 1.5 percent of the plate's half-width out of focus finds no plate; widening it
changes `ring-layout.jsonl` on both apps.

## How it behaves

- **Sender.** "Use a code instead" shows the ring code for a song that has a video id: the album art in the middle disc, five rings of round
  dots in the app's accent colour on a flat plate (tone 95 of the same hue), the orange start dot, the sway and, near another phone, the
  tighten and glow. A fresh tag every 60 s. "Use QR code instead" appears 6 s after the code came up (a sender cannot see the receiver's
  scan) and swaps the ring code for the plain QR; the two are never side by side. A song with no video id shows the QR at once with one
  line saying why.
- **Receiver.** "Scan a code instead" opens the camera for the ring code (the permission flow is the existing one). The camera runs only
  while this screen is open, the app is in the foreground and the session waits for a song (not during a beam). Three equal fresh reads in
  a row look the song up (needs internet), then the usual card, consent, save and Undo. "Use QR code instead" appears after 6 s of a scan
  that reads nothing (a scan that keeps decoding codes that never agree is "working" and gets two seconds more), at once with no camera,
  after a camera failure or a too slow scanner, and after an expired code, a code from the future or a failed lookup. A repeated code says
  "You already took that code." and does not offer the QR. The QR scanner itself opens only behind that button, with "Back to the Song
  Tap code" beside "Back to touching phones".
- **Drawing.** One `Canvas` inside a `TimelineView`: 30 frames a second while idle, the display's rate in a beam, and not at all while the
  view is off screen, the app is in the background, or Reduce Motion is on and nothing beams. The geometry of the 200 dots is built once per
  code and size (two cached paths), a frame is two fills, the outline and the start dot; the beam draws the 200 dots one by one for 2 s.
  The motion is `RingCodeTimeline.frame` (the same timeline as Android), the art disc breathes, pulses and lifts through `scaleEffect` /
  `offset` / `opacity`. No blur, no glass.
- **Diagnostics.** The scanner's own grey frame turned upright with the plate circle (green), the art circle (cyan) and the start dot
  (orange), the frame and scan rate, the last scan's time, dots matched of 200, Reed-Solomon fixes and erasures, the 200 slot confidences,
  the last 20 results with Copy log, and the code at this phone's colour in light and dark mode with the contrast figures and a "Play the
  beam" button. It does not arm Song Tap.

## Deviations from Android and from RING-CODE-SPEC.md

1. The dots are the app's accent colour (the spec's iOS default), not a dynamic colour; the plate is tone 95 of it. The preview in the
   diagnostics shows the accent's light and dark schemes.
2. The Android `RingCodeResolver` is `AppRingCodeLookup` over `RadioSource.hydrate`: one `get_queue` request out of the brain's request
   budget (the YouTube host budget) instead of a bare client call.
3. The luma plane is copied row by row with `memcpy` semantics (`copyMemory`) rather than through Accelerate: the copy is a straight
   byte move, and the scanner already does its own box downscale; there is nothing for vImage to add.
4. The frame is not rotated before scanning (the scanner does not care); the diagnostics picture is turned upright with a fixed 90
   degrees (the back camera in portrait), not read from the device's orientation.
5. The sender's "Use QR code instead" shows 6 s after its code is up, as on Android. Over the code route the sender never learns of the
   scan, so the ring beam is seen on a Bluetooth beam and in "Play the beam" in the diagnostics.
6. With no camera at all the QR button is still offered (as on Android), though the QR scanner needs a camera too. The iOS Simulator has no
   camera, so a simulator run shows exactly that state.
7. Android's `RingCodeFlowTest` drives the state holder over a Bluetooth rig; the iOS controller compiles only on CI, so the same decisions
   are tested through `RingScanSession` + the real `SongTapEngine` over its fake port, and the sender's choices as `RingSendPlan`.
8. One Android test is not ported: the real `get_queue` answer through `InnerTubeMusicParsers`, because PixlLibrary's tests cannot import
   PixlNet. `InnerTubeRadio2aTests` already covers that parser.

## Cut or deferred

- `NearbyInteraction` stays out (a later stage). No Info.plist change was needed (the camera and Bluetooth strings were already there)
  and `ci/check-forbidden.sh` needed no new import: `AVFoundation`, `CoreMedia` and `CoreGraphics` were already allowed.
- Reading the orientation for the diagnostics picture (above), a torch toggle, and a manual focus tap on the preview.
- The sender does not learn that a ring code was scanned (no back channel), so no "Sent" pill after a scan.

## How to test with two phones

1. Settings › Song Tap on both phones: Allow Song Tap on. On phone A play a song that came from YouTube Music or a Spotify song that has
   been matched (it has a video id).
2. Phone A: Song Tap › Send › "Use a code instead". You see the ring code. Phone B: Song Tap › Receive › "Scan a code instead" and allow
   the camera. Hold B about an arm's length away, the whole code inside the circle, A's brightness up. Three good reads, "Looking up the
   song", then the card; "Add" saves it, Undo takes it back.
3. Try the hard cases while Developer mode's Ring code diagnostics is open on B (Settings › Song Tap): a tilted phone, a dim room,
   glare from a lamp, a smudged screen, a code from the side. Read the slot map: green is sure, amber weak, red unknown.
4. Hold B at the screen without a code (or at a wall) for 6 s: "Use QR code instead" appears; tapping it opens the QR scanner, and
   A's "Use QR code instead" swaps the ring code for the QR.
5. Turn Airplane mode on for B while scanning: "Couldn't look the song up. Check your connection, or use the QR code."
