# Pixl ring code, iOS (2026-11-21)

Branch `everything`. This is milestone R1: the pure core, the renderer and the scanner, ported from Android's `:songtap` ring
code (`handoff/2026-11-21-ring-code.md` on the Android repo). There is no screen, no camera and no Canvas drawing yet (the next
milestone, on both apps), and **nothing here has run on a phone or in the iOS CI yet**: it is verified by the Windows PixlCore
test run (the same tests as Android's, with Android's seeds) and, once pushed, the `ci` workflow.

The design is `builds/song-tap-code-design/RING-CODE-SPEC.md` (approved 2026-11-20). Order of ways to beam: the Bluetooth tap,
the ring code, the plain QR last ("Use QR code instead" after about 6 s of failed ring scanning, or when the camera cannot run the
scanner). The code carries only the video id and a tag; a song with no video id (never matched) cannot use it and goes the QR way.

## Files

`Packages/PixlCore/Sources/PixlLibrary/SongTap/ring/` (integers only, replayed against Android's goldens bit for bit; the purity
test keeps floating point and Foundation out):

| File | What |
|---|---|
| `RingCodeLayout.swift` | the 200 slots (five rings of 24/32/40/48/56), geometry in permille of the plate half-size (art 280, outline ring 305..330, ring radii 420..800, start dot at 895), byte map (byte b owns slots 8b..8b+7) |
| `Gf256.swift`, `ReedSolomon.swift` | GF(256) (0x11D) and RS(25,11): `2e + s <= 14`. `Gf256.pow` is `Gf256.alphaPow` here (the purity test bans a call named `pow(`) |
| `RingCodePayload.swift` | `RingCodePayload`, `RingCodePayloads` (`pack`, `unpack`, `encodeSlots`, `fromCodeword`, `bucketOf`, `freshness`), `RingUnpack`, `RingReject`, `Freshness`: 11-char video id (6 bits each) + 6-bit minute bucket + 8 random + CRC-8 |
| `RingCodeTimeline.swift` | `RingFrameBuffer` and `RingCodeTimeline.frame / frameInto` (idle sway, approach, beam, pill, Reduce Motion), a pure function of the millisecond |

The numbers are the same as Android's because the same seeds draw the same pictures (next section). Limit lines (6 trials a step):
tilt 60 degrees 6 / 6 and 70 degrees 0 / 6, noise sigma 48 6 / 6 and 64 4 / 6, contrast 0.25 5 / 6 and 0.18 0 / 6, plate 130 px

That says nothing about a release build on an iPhone; it is only the test's floor (the test asserts under 2 s).

## Across the platforms (`Fixtures/songtap-ring`)

`scenes.jsonl` is 12 scenes (a code and integer parameters), `kotlin/*.pgm` are those scenes drawn by Android's **committed**
`RingCodeRenderer` (commit 4f0aaed): I compiled the committed ring sources with `kotlinc` and ran a small harness, no Gradle.
- Swift reads what Kotlin renders: 12 / 12 (`swiftReadsWhatKotlinRendered`).
- The Swift renderer draws the same pictures: byte for byte on Windows (`cmp` on all 12 when the files were made, mean difference 0,
  worst 0). The test allows a mean difference under 0.5 and under 0.2 percent of pixels more than 8 levels off, so another maths
  library may move an edge pixel.
- The reverse (Kotlin reads what Swift renders) follows from the identical bytes, and I also ran Android's committed scanner over
  the Kotlin pictures: 12 / 12, and over its own fresh renders: 12 / 12.
- Android has no test over these files yet. To add one: read `scenes.jsonl` (the keys are in `Fixtures/songtap-ring/README.md`),
  render with `RenderParams`, scan, and compare with `kotlin/*.pgm` or scan the PGMs directly.

## Deviations from the Android port

1. The names: `Gf256.alphaPow` (not `pow`), `RingCodeTimeline.beamTotal(reducedMotion:)` (Kotlin's `beamTotalMs(...)`, a name taken by a constant).
2. ARGB colours are `UInt32` (Kotlin's `Int`); `RingCodeLayout.markerArgb` stays an `Int32` because the golden file prints it signed.
3. The scanner's trace strings are shorter (no number formatting); the sort for the blob list, the outline list and the byte order
   breaks ties by index, which is what Kotlin's stable sort does.
4. Kotlin's Byte arithmetic in the renderer's smudge overlay of the orangeness map is reproduced on purpose (a signed Byte times a
   Double), so the maps match; it only matters as a tie-breaker in the scanner.
5. The long fuzz loops run fewer rounds (Swift Testing runs in debug): see `docs/test-parity.md`.

## Not on this milestone (cut or deferred)

- The Song Tap screen changes (show the ring code, Receive with the camera, "Use QR code instead" after 6 s), the AVFoundation
  frame source and the `CVPixelBuffer` to `RingFrame` conversion (a luma plane copy, plus `RingHue.orangeness` per chroma sample
  if wanted; the hue map is optional), the SwiftUI Canvas drawing and its `TimelineView`, the Developer mode scan-diagnostics view.
  The core is ready for them: `RingCodePayloads.encodeSlots`, `RingCodeLayout` geometry, `RingCodeStyle.palette(accent)`,
  `RingCodeTimeline.frameInto`; `RingScanner.scan` on one background queue, `RingScanAccumulator` for the 3-in-a-row rule,
  `RingCodePayloads.freshness` for the tag.
- No `ci/check-forbidden.sh` import change was needed (AVFoundation, CoreImage, CoreBluetooth and CoreMotion were already allowed)
  and no Info.plist change (the camera string is already there for the QR scanner).

## Unverified

Everything on a device: scan reliability on real cameras, dim light, real screen glare, distance, moire, scan time on an iPhone
(release build, Accelerate for the downscale is not used yet), how the accent-coloured dots look on the plate. The tests render
synthetic pictures with simple glare and smudge models. The blur cliff Android found is the main known weakness: the outline ring
is 25 permille thick, so a frame more than about 1.5 percent of the plate's half-width out of focus finds no plate; widening it
changes `ring-layout.jsonl` on both apps.

## How to run

```
cmd //c "ci\\swiftw.cmd test --package-path Packages\\PixlCore --filter RingGoldenTests"
cmd //c "ci\\swiftw.cmd test --package-path Packages\\PixlCore --filter RingScannerTests"   # the sweeps, about 2 minutes in debug
```

Two phones: nothing to show on a phone until the next milestone. Then: open Song Tap on phone A with a matched song, scan with
phone B in bright light at arm's length, then dim light, a tilted phone and a smudged screen, with Developer mode's scan
diagnostics open to read the per-slot confidence.
