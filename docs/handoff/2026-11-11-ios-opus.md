# iOS: Opus instead of AAC (2026-11-11, branch `audio-opus`)

Owner of this work: the OPUS agent of the 2026-11-10 plan (`ios-integration-map.md` on `audio-foundation`, sections 4,
9, 10, 11). Status and test results are at the end of this file; the design comes first, as it was written before
the code.

## Why

iPhones play itag 140 (AAC-LC 128 kbps, nothing above about 16 kHz) because AVPlayer does not read WebM; Android plays
itag 251 (Opus, about 130-160 kbps, full band). An Apple media engineer wrote that Opus is supported from iOS 17
"only in MP4 files" (developer forums, thread 759210; checked again today, the answer is hedged with "so far as I am
aware" and the question was about fMP4 HLS). Our deployment target is iOS 26, so every supported phone has the
decoder. Repackaging the WebM into MP4 (no re-encoding) keeps the audio bit for bit.

## Rules this design keeps

- **No start-up latency.** The song that starts cold keeps playing AAC exactly as today. Opus is only used when a
  complete, checked Opus file is already on disk when the player asks for the song.
- **Nothing gets worse.** Any surprise (no Opus offered, odd WebM layout, remux error, size or duration mismatch, the
  system decoder refusing the file, the player refusing it) means AAC, silently, and the failure is remembered for
  that video. Android's format choice (`pickBestAudio`, the golden file) is untouched; iOS gets an extra choice.
- Downloads stay AAC (`Downloads/<videoId>.m4a`). Offline files, Sing and cloud jobs keep reading what they read.
- Only my files (map section 11): `PixlNet/YouTube/*`, `PixlNet/Stream/*`, new `PixlNet/Remux/*`,
  `App/Services/YouTube/*`, their tests. Nothing in `App/Playback/`.

## The pieces

### 1. PixlNet `Remux/` (pure Swift, builds and tests on Windows)

- `OpusWebMReader`: EBML header (DocType `webm` or `matroska`), Segment (known or unknown size), Info
  (TimestampScale, Duration), Tracks (exactly one audio track `A_OPUS`, CodecPrivate = OpusHead, CodecDelay,
  SeekPreRoll; ContentEncodings refused), Clusters (known or unknown size) with SimpleBlock and BlockGroup
  (Block, BlockDuration, DiscardPadding), all three lacing kinds (Xiph, fixed, EBML), Void and CRC-32 anywhere,
  SeekHead / Cues / Tags / Chapters skipped. Output: OpusHead fields, every packet with its timestamp, the
  end trim.
- Every packet's length in samples comes from its TOC byte (RFC 6716 section 3.1), never from the 1 ms WebM
  timestamps. Checks that reject the file: no Opus track or more than one, empty or malformed packets, a packet over
  120 ms, timestamps that drift from the sample count by more than 3 ms (a gap or overlap would shift everything
  after it), CodecDelay disagreeing with the OpusHead pre-skip, channel mapping family other than 0 (mono/stereo;
  YouTube music is stereo), an end trim longer than the last packet.
- `OpusMP4Writer`: a plain (not fragmented) MP4, `moov` before `mdat`. Layout, following the Opus-in-ISOBMFF
  encapsulation spec (opus-codec.org, version 0.8.1):
  - `ftyp` major `isom`, minor 512, compatible `isom iso2 mp41 Opus` (`iso2` because roll groups are required).
  - `mvhd` and `mdhd` timescale 48000 (sample-exact edits); `tkhd` enabled, in movie, volume 1.
  - `edts/elst` (required by the spec): one edit, `media_time` = pre-skip, `segment_duration` = valid samples
    (all samples minus pre-skip minus the WebM end trim). This is what removes the pre-skip, so no click and the
    first sample is at 0.
  - `stsd` with an `Opus` sample entry (channelcount = OutputChannelCount, samplesize 16, samplerate 48000 << 16)
    holding `dOps` (version 0, big-endian: OutputChannelCount, PreSkip, InputSampleRate, OutputGain,
    ChannelMappingFamily).
  - `stts` from the TOC durations; the last sample is shortened by the end trim (spec 4.3.4). `stsz` per sample,
    `stsc` + `stco` in chunks of about one second, no `stss` (every Opus sample is a sync sample).
  - `sgpd` + `sbgp` `roll` with roll_distance = minus the number of packets covering 80 ms (3840 samples), computed
    per packet like ffmpeg's muxer.
- `OpusRemuxer.remux(webm:)` glues the two and returns the MP4 bytes plus a summary (packets, pre-skip, end trim,
  valid samples, channels, duration). Pure function of the input bytes.

Why not ffmpeg's own output as the reference: on the test fixture `ffmpeg -c copy` to MP4 rounds through the WebM
millisecond timestamps (first sample 1008, edit media_time 336) and decodes to 624 samples more than the WebM. Ours
is exact by construction and checked against the WebM's own decode.

### 2. Which stream is Opus (PixlNet `YouTube/`)

- `AudioFormatPolicy.opusUpgrade` + `AudioFormatSelection.pickOpusUpgrade`: the best `audio/webm` Opus format of at
  least 100 kbps (so itag 251, never 249/250), under the user's streaming-quality cap (no fallback over it), and only
  when its bitrate is higher than the AAC pick of the same response (a 256 kbps itag 141 stays AAC).
- `PlayerResponseMemo`: the AAC resolution records each `player` response for a few minutes; the Opus resolution
  reads it before asking YouTube, so on the usual path (VISIONOS) choosing Opus costs no extra request. The AAC path
  always asks YouTube live, as today (its 403 retries must get fresh URLs).
- `InnerTubeService.resolveOpus(videoId:)`: the same client chain with the Opus policy, no hedging, no probe. Also
  returns YouTube's own durations of both streams (`dur` in the two URLs) for the duration check.

### 3. Preparing a file (`App/Services/YouTube/Opus*.swift`)

- When: by the prefetcher, inside its existing plan task (so a queue change, a skip or a pause cancels it):
  1. the next song in auto-advance order, once the current song has played 10 s;
  2. then the current song itself, once it has played 30 s (its next play is Opus).
  Only on an unmetered, unconstrained network (Wi-Fi or Ethernet, not a hotspot, not Low Data Mode), not in Low
  Power Mode, not under memory pressure, not in safe mode. Allowed while the app is in the background, because
  that is when people listen. Never for a downloaded song.
- How: resolve Opus, download the whole WebM in 2 MiB ranged GETs with the client's User-Agent and the same
  `CloudStreamSecurity` checks as streaming (safe host, audio content type, sane length; at most 20 MB; one
  re-resolution on 403/410), remux in memory, then check the result with the system's own decoder before anyone can
  play it: one audio track, format Opus at 48 kHz with the expected channels, `isPlayable`, duration equal to the
  valid samples within 2 ms, and a full `AVAssetReader` decode whose frame count equals the valid samples (within 64
  frames) and which is not silent. Only then is it renamed to `Library/Caches/YouTube/opus/<videoId>.mp4` (atomic).
- Duration against AAC: YouTube's `dur` of the Opus and AAC streams must agree within 50 ms (the engine's own
  tolerance for an in-song switch), else AAC for that video.
- Storage: its own folder under Caches (Settings › Offline storage measures and clears it with the rest), 500 MB,
  least recently used first, never a file used in the last 10 minutes.

### 4. Playing it

- `StreamingPlayableURLResolver.playableURL`: downloaded file, then **the Opus file**, then the complete AAC cache
  file, then `pixlstream://`. A file-exists check, no await on the network: no added latency.
- `recoverPlayableURL`: when the failed URL is an Opus file (the engine asks once after `loadTracks` fails), the
  file is deleted, the failure remembered, and the AAC URL for the same video is returned. Spotify's resolver
  passes file URLs down to us, so a Spotify song keeps its match.
- The video id rule of the map (4.2) holds: the id is the file name without its extension.

### 5. Remembering failures

Per video, in `opus/state.json`: no Opus offered (7 days), network (30 minutes), remux / verify / duration / player
refused / too large (30 days). Global: five Opus resolutions in a row without an Opus format pause attempts for a
day (so a client that stops offering Opus costs nothing), and if the system decoder refuses the first two files
on an OS build where none ever worked, Opus is off until the OS version changes.

### 6. Timeline (lyrics, Sing, renders)

- Positions: the edit list removes exactly the pre-skip, so position 0 is the first real sample, like AAC.
- Duration: the item duration is the valid sample count; the gapless hand-over and the scrubber use it.
- Sample rate: Opus is 48 kHz; the tap already redesigns per item rate (map 9.4).
- Sing and cloud jobs read the resolver's file. An Opus file goes the existing `.decode` route of
  `CloudAudioPreparer` (only AAC is copied) and `AudioPCMReader`, both `AVAssetReader`, the same decoder the check
  above used. A render or instrumental made from the AAC decode may sit a few ms off the Opus one (map 9.4); the
  length check of the in-song switch still holds because of the 50 ms rule above.

### 7. Diagnostics

The Test playback report gets an "Opus" step for the tested song: playing from the Opus file, ready for the next
play, not prepared yet, or AAC with the remembered reason.

## Tests

- PixlCore (Windows and CI `core`): a real ffmpeg-made WebM fixture (3 s stereo sine, libopus 64 kbps, cues at the
  front like YouTube's files), plus edge-case files written by the test itself from the fixture's packets (unknown
  sizes, Xiph / fixed / EBML lacing, BlockGroups with and without DiscardPadding, Void and CRC elements, bad inputs).
  The MP4 is read back with a small box parser in the test: brands, sample count, durations, dOps fields, edit list,
  chunk offsets pointing at the right bytes, roll groups.
- Format choice and memo tests next to the existing `AudioFormatSelectionTests`; Android's golden file untouched.
- App (CI simulator): the fixture remuxed and opened with AVFoundation (track format, duration, full decode count).
- `tools/opus/check-remux.sh` (not CI): ffprobe and ffmpeg read our MP4 and its decode is compared with the WebM's.
